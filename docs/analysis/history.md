## ⚠️⚠️ 覆した結論（ここがこの文書の本題）

**5 回、自信を持って間違えた。** どれも「実機で動いた／動かなかった」という
一見強い根拠を持っていたのに、原因の特定を間違えていた。

### 1. 「`PERIPHERAL_LOGIN` には応答してはいけない」→ 応答するのが正解

参加直後に器具が送ってくる `01 19` + 16 バイトに対して、エコーバックで返したら
**12 回すべて切断された**。応答しなければ WELCOME まで進んだ。
そこから「応答してはいけない」と結論した。

⚠️ 切断されていたのは「応答したから」ではなく **「エコーバックという誤答をしたから」**。
正しい応答は計算できる（LOGINKEY で復号 → HOMEID + パスワード + 鍵 + PKCS#7 を返す）。
正しく応答すると器具が状態も返してくれる。 → [02 C23-2](../02-protocol.md)

⭐ この誤りのせいで「状態は取れない」と一度は判断していた。取れた。

### 2. 「`SET_LINK` を送らないと数秒で切れる」→ 主リンクには送ってはいけない

公式アプリのログと比べて唯一送っていなかったのが `01 10` (`SET_LINK`) で、
送るようにしたらリンクが数秒 → 90 秒以上に伸びた。

⚠️ 伸びた本当の理由は別のところにあり（切断の真因は上記 1 のログイン無応答）、
`SET_LINK` は **2 台目以降のバックアップリンク専用** だった。
全器具に送ると **器具が応答を返さなくなる**。 → [02 C23-6](../02-protocol.md)

### 3. 「器具はコントローラのアドレスを記憶している」→ 記憶していない

同じ広告アドレスでは再接続してこなくなり、ランダムアドレスに変えたら 1.9 秒で
復活した。そこから「アドレスを覚えられている。回転させる必要がある」と結論した。

⚠️ 真因は BlueZ がプロセス終了後も ACL リンクを保持していたこと。
古いリンクを切れば **同じアドレスでも約 5 秒で再接続してくる**。
3 条件の実験で切り分けた。 → [02 C31 / C32](../02-protocol.md)

⭐ この誤りは Android 版の設計を歪めていた（「Android は広告アドレスを制御できないので
不利」という前提が消えた）。

### 4. 「送信はゼロパディング・XOR なし」→ PKCS#7 + AES の後に XOR ホワイトニング

`sendEncry` が AES の外側で XOR をかけていた。 → [02 C23-5](../02-protocol.md)

### 5. 「取りこぼすので 3 連射する」→ 1 通で足りる。連射が自壊の原因だった

送信 1 通あたりの到達率は実測 **0.993〜1.000**。
⚠️ しかも「同じ PDU が二重に届く」という別の悩みの原因も **自分の 3 連射** だった。
→ [02 C33-5](../02-protocol.md)

### おまけ: アドバタイズの持続時間

当初「数百 ms」と書いていたが、実測は **21〜95 秒 出しっぱなし** だった。

## ⭐ 効いた発見 3 つ

覆した結論とは逆に、当たって効果が大きかったもの。

### 1. アプリの ID 表示 8 桁 = HOMEID 4 桁 + パスワード 4 桁

公式アプリのメニュー画面に出ている番号がそのまま認証情報だった。
**変換方法が両者で違う**（HOMEID は 10 進数の LE 4 バイト、パスワードは ASCII 4 バイト）。
→ これで 器具の登録を公式アプリに任せ、新実装は「参加するだけ」でよくなった。
→ [02 C16](../02-protocol.md)

### 2. PDU は平文で流れていた

照明制御（`DATA_EVENT`）は暗号化されていない。暗号化されるのは PDU タイプ `0x06` と
ログイン（`0x19`）だけ。→ `.so` を使わない完全自前実装が視野に入った。
→ [02 C18](../02-protocol.md)

### 3. 鍵は器具が自分から渡してきていた

`PERIPHERAL_LOGIN` を LOGINKEY で復号すると `[0..3]` = HOMEID、
`[4..7]` = **そのリンクの XOR ホワイトニング鍵**。
あとは `XOR → AES_ECB_decrypt(EVENTKEY) → PKCS#7 除去` で平文になる。
→ [02 C23](../02-protocol.md)

⭐ 鍵導出も `.so` の静的解析（シンボルが全て残っていた）で完全に解明した。
HOMEID とパスワードを 1 バイトずつ交互に並べ、後半に固定文字列を足すだけ。

```
鍵1（コマンド用）: D2 35 04 36 00 37 00 38 + "LOGINKEY"
鍵2（イベント用）: D2 35 04 36 00 37 00 38 + "EVENTKEY"
                   └ homeid/pwd 交互 ┘   └ 固定 ┘
```

⚠️ 当初は「AES が標準実装ではない（独自 S-box か）」と判断して
`.so` の `ctypes` 呼び出しを検討していたが、**標準の AES-128-ECB だった**。
再現できなかったのは XOR ホワイトニング（覆した結論 4）を見落としていたため。
→ [02 C21 / C22 / C23](../02-protocol.md)

## 実装が公式アプリを超えた点

`odelicd` の実測（→ [02 C33](../02-protocol.md) / [06](../06-raspberrypi-setup.md)）。

| | 公式アプリ | `odelicd` |
| --- | --- | --- |
| 起動〜操作可能 | 約 7 秒 | 0 秒（常時接続維持） |
| 1 操作の所要時間 | 不明・確認なし | 5〜8 ミリ秒 |
| 効いたことの確認 | しない | `?wait=1` で 277〜320 ms（収束を確認して 200 / 未確認なら 504） |
| 取りこぼし対策 | 送信 1 回のみ | 1 通 + 状態応答で確認して再送（到達率 0.993〜1.000） |
| リンクの維持 | — | 寿命 p50 152 秒（旧実装は 7〜14 秒で切り合っていた） |
| 状態要求の往復 | — | p50 50〜78 ms / p90 60〜92 ms / max 77〜117 ms |
| 未接続のとき | 「接続成功」と表示する | HTTP 503 + キューに保持 |
| ナイトライトの状態 | 読んでいない（`data[7]` を無視） | 読んで反映する（→ [02 C24-5](../02-protocol.md)） |
| 分割 PDU の再組立 | 1 個落ちると以降二度と完成しない | 欠落を検知して破棄・タイムアウトあり（→ [02 C30](../02-protocol.md)） |

⚠️ **不安定さの主犯はこちら側の実装だった** という発見が大きい。
BlueZ が Connection Parameter Update Request を 65 本送って器具の指定した
15.00 / 28.75 ms を **45 ms に書き換えていた**（`conn_min_interval` で解決）。
広告を出し続けると新リンクが確立するたびに器具が古いリンクを切り、
3 分で 22 回も参加し直していた（参加後は接続の受け付けを止めて解決）。

## 閉ループを実機で確認した記録

指示した値が器具から読み戻せることの確認（2026-07-25）。

| 指示 | 器具が返した状態 |
| --- | --- |
| `bright=60&color=50` | `on=true bright=60 color=50` ✅ |
| `off` | `on=false` ✅ |
| `night?level=0` | `night_level=0`（器具値 3） ✅ |
| `night?level=1` | `night_level=1`（器具値 2） ✅ |

⭐ ナイトライトの状態は `0x71` 応答の `data[7]` にある。
公式アプリはこのバイトを読んでいないので、自前実装のほうが正確に追える。

### 他コントローラの操作も追従できる

器具は状態変化を自発通知しないが、**他のコントローラが送ったコマンドは平文で
中継されてくる**。公式アプリで操作しながら Pi で観測して確認した。

```
<< 03 FF FF FF FF 20 25 00 00 00 C1 37 37 ... 01   点灯（グループ1）
<< C1 00 12 → C1 00 03 を 16 連射                   明るさスライダー
<< 03 FF FF FF FF 20 25 00 00 00 C5 00 01 ... 01   ナイトライト level 1
```

- `src vAddr`（`25 00 00 00` = スマホ）が自分と違えば他人の操作と判る
- ⚠️ 同じ PDU が **二重に届く**（中継経路が複数）→ 重複排除が必要
- ⚠️ 公式アプリは明るさの中間値を **16 通も連射** していた（約 143 ms 間隔）
- ✅ 共存問題なし。 公式アプリが操作中も Pi のリンクは 1768 秒継続

⭐ 観測した `C5 00 01 … 01`（グループ 1・level 1）に対して器具が `night=2`（= level 1）を
返した。ナイトライトの解読が公式アプリの実トラフィックで独立に裏付けられた。
→ [02 C28](../02-protocol.md)

### 複数器具への対応

器具が別グループ（0 と 1）に入っていたため、グループ 0 だけに送ると 1 台しか
反応しなかった。既定を「全器具一斉」（`MSGID 0xC0` + チャネル `0x2A`）にして解決。

## 環境

| 環境 | 用途 |
| --- | --- |
| 開発機（Windows） | 静的解析・ドキュメント・ツール |
| Android 実機（Pixel 9 / Android 17） | 公式アプリの HCI ログ採取。照明から離れた場所で |
| Raspberry Pi 3（`odelic-re-connected`） | 照明のそばに常設。自前実装の実行と `btmon` 観測 |

Pi は Tailscale 経由で SSH でき、`btmon` で完全な HCI トレースが取れる。
Android の bugreport 経由（`btsnooz`）はスキャン結果がフィルタで欠落するが、
Pi ならその制約がない。

| 対象 | 状況 |
| --- | --- |
| 解析ツール | adb 37.0.1 / jadx 1.5.6 / 自作 btsnoop パーサ |
| 解析対象 APK | `jp.co.odelic.smt.remote10` v1.9.36 (vc133) |
| 対象照明器具 | `PLTCEOC-05` 2 台（`EC:C5:7F:81:DE:CD` / `EC:C5:7F:80:28:A6`） |
| 無線モジュール | Cypress CYW207xx 系（ARM Cortex-M4 / Bluetooth 5 / 外付け 8Mbit SPI Flash） |
| BLE スニファ | ⏸ 未手配（必要になったら nRF52840 Dongle を Pi に接続） |

⭐ 公式アプリには Pairlink「Connected Mesh」SDK が難読化されずに丸ごと含まれていた。
`libnative-lib.so` もシンボルが全て残っていた。これが解析を成立させた最大の理由。

⚠️ **器具のファームウェアが APK に同梱されていた**（`assets/ota/*.mp3` は音声ではない）。
暗号化はされていないが独自コンテナで圧縮されており、そのままでは逆アセンブルできない。
