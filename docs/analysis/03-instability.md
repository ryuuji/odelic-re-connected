# 03. 接続不安定の原因仮説

最終更新: 2026-07-25（静的解析フェーズ 2 の結果を反映）

「なぜ公式アプリは不安定なのか」の原因候補を洗い出し、検証方法と対策をセットで持つ。
[01-findings.md](01-findings.md) の症状 S1〜S8 と対応づける。

---

## ⚠️ 前提の訂正：方式は GATT ベースだった

当初はコネクションレス・アドバタイジング方式（仮説 H1）を前提に原因を組み立てていたが、
静的解析で **誤りだと判明した**。実際は Pairlink「Connected Mesh」SDK による
**GATT 接続ベースのメッシュ** で、スマホは Central または Peripheral（GATT サーバ）として
1 台の器具と接続し、そこを入口にメッシュ全体へコマンドを流す。
→ 詳細は [02-protocol.md](../02-protocol.md) の C2。

方式が変わっても、症状の説明としての骨格は概ね維持された。
「到達確認と再送が無い」「状態を毎回集め直す」という構造的な問題は
アドバタイズ方式でも GATT 方式でも同じように成立する。
ただし個々の原因候補は確度が変動したので、以下に反映してある。

## I7. セグメント欠落を検知せず、復旧もしない ✅ 確定

**最も厄介な症状群（S4 グループ設定の保存失敗、S5 保存直後に操作不能、
S6 初期化しか復旧手段がない）の根がここにある。**

### 確定した根拠

`MeshCommon.processSegmentPDU()` の実装。

```java
byte b = bArr[2];
int seq   = b & 0x0F;          // 下位 4bit = シーケンス番号
int total = (b >> 4) & 0x0F;   // 上位 4bit = 総セグメント数
if (seq == this.current_seq + 1) {
    System.arraycopy(bArr, 3, this.segment_data, this.segment_data_offset, bArr.length - 3);
    this.segment_data_offset += bArr.length - 3;
    this.current_seq = seq;
    if (total == seq) { /* 完成して返す */ }
}
return null;   // ★ 番号が飛んだら黙って破棄
```

問題は **5 点**（当初 3 点としていたが、精読して 2 つ追加 → [02 C30](../02-protocol.md)）。

1. **欠落の検知が無い**。`seq != current_seq + 1` なら `null` を返すだけ。
   上位に「失敗した」という情報が伝わらない
2. 状態のリセットが無い。`current_seq` と `segment_data_offset` が
   中途半端な値のまま残る。→ 一度落とすと以降の再組み立てが永久に失敗する
3. タイムアウトが無い。途中で送信が途絶えても、いつまでも待ち続ける
4. ⚠️ **`current_seq == 1` で固まった場合は、次の転送の seq 2 が
   「期待どおり」として受理されてしまう** → 前の転送の残骸と混ざった
   壊れたデータが、エラーにならずに上位層へ渡る
5. ⚠️ バッファ長を検査していない。 `segment_data` は 255 バイト固定だが、
   実機の MTU は 217（1 通 214 バイト）なので 2 セグメントで 428 バイト に達し
   `ArrayIndexOutOfBoundsException` になる

セグメント数は 4bit なので最大 15。

⭐ 分割は 復号より下の層（`processData` の手前）にあるので、
暗号化された長い応答も分割されて届く。

### なぜ S4〜S6 になるのか

`DATA_EVENT` のメッセージデータは **最大 9 バイト**（`MeshProfile.createDataEvent`）。
明るさ・調色のような単発コマンドは 1 パケットに収まるが、
グループ設定のような複数バイトの構成情報はセグメント分割が必要になる。

分割された設定書き込みの途中で 1 パケット落ちると、
器具側は中途半端な設定を持ち、アプリ側は成功したと思い込む。
以後アプリと器具の認識がずれ、操作が効かなくなる（S5）。
アプリからは直せないので初期化しかない（S6）。

### 対策（新アプリ）

- 設定変更を **冪等な操作として設計** し、何度送っても結果が同じにする
- 書き込み後に状態を読み返して **実際に反映されたかを確認** し、一致するまで再送する
- セグメント送信は 自前で管理 し、タイムアウトと全体リトライを持つ
  （Pairlink SDK の Java 層を流用する場合、この関数は使わず上位で組み直す）
- 確認できるまで UI に「保存しました」と表示しない（P4）
- 破壊的操作の前に現在の設定を読み出して保存しておく

### ✅ 受信側は `odelicd` で実装・検証済み（2026-07-25）

上の 5 つの欠陥を全部直した再組立を実装した（→ [02 C30-3](../02-protocol.md)）。

| 直したこと | 内容 |
| --- | --- |
| 欠落の検知 | ログに出して即破棄。溜め込まない |
| 状態のリセット | `seq == 1` は常に新しい転送として作り直す（残骸で詰まらない） |
| タイムアウト | 3 秒 |
| バッファ上限 | 4096 バイト。超えたら破棄 |
| 送信元の区別 | MAC ごとに独立した組み立て状態 |

検証では「1 個欠落 → 破棄 → **直後の正常な転送は成功する**」を確認した。
公式アプリはここで永久に壊れる。

## I11. GATT 接続そのものが切れる／再接続が遅い（新規）

**内容**
方式が GATT ベースだと判明したことで浮上した候補。
スマホは 1 台の器具と GATT 接続し、そこが **メッシュ全体への唯一の入口** になる。
この接続が切れれば 全器具が一斉に操作不能 になる。

`MeshService` には接続状態の定数が多数ある。

```
MeshStatusConnecting = 1     MeshStatusReconnecting = 2
MeshStatusConnected = 3      MeshStatusConnectionReady = 4
MeshStatusDisconnected = 5   MeshStatusWelcome = 6
MeshStatusWrongPwd = 9       MeshStatusAlreadyConnected = 10
MeshStatusJoinFail = 12      MeshStatusJoinStarted = 13
```

`MeshStatusAlreadyConnected`（応答コード 8 = "Already Connected"）が存在することは、
入口の器具が既に他のコントローラと接続済みで繋げない ケースがあることを意味する。
リモコン 4 台まで併用できる（[01-findings.md](01-findings.md)）仕様と合わせると、
接続枠の競合が起きうる。

検証方法
- HCI ログで `LE Connection Complete` / `Disconnection Complete` の頻度と間隔を測る
  → `python docs/analysis/tools/btsnoop.py summary` が接続イベント数を出す
- 操作不能になった瞬間に切断イベントがあるかを `timeline` で確認
- 入口の器具を意図的に電源 OFF して、再接続に何秒かかるか測る

✅ 実測で確定（2026-07-25）→ [02-protocol.md](../02-protocol.md) C33-3 / C33-8 / C33-9

切断は確かに起きていた。しかも 主犯はこちら側の実装だった。

| 指標 | 実測 |
| --- | --- |
| リンク寿命 p50 | 7〜14 秒（広告を出し続けていた期間） |
| 3 分間の再参加回数 | 22 回 |
| 切断理由 | `0x13` 器具が切った 36 / `0x08` 電波断 24 / `0x16` 自分 5 |
| 切断 → 次の接続までの空白 | p50 3.3 秒 / p90 4.2〜5.2 秒 |

⭐ **真因: 広告を出し続けると器具が次々に繋いできて、そのたびにメッシュが
古いリンクを切る**（新リンク確立の 0.7〜1.4 秒後・完全な交互パターン）。
メッシュは「コントローラ 1 台につきリンク 1 本」しか許さない。

⚠️ したがって「入口を冗長化する（複数の器具に同時に繋ぐ）」は誤りだった。
2 本目を迎えようとすると 1 本目を失う。正しいのは
1 本を長く維持し、切れたら次の 1 本に繋ぎ直すこと。
リンク 1 本でもメッシュが中継するので 全器具を制御・監視できる
（接続していない器具の状態応答も RTT 78 ms で返ってきた）。

さらに BlueZ 5.82 は切断時に `StopNotify` をほぼ呼ばない（24 時間で
確立 50 回に対し切断 2 回しか記録されていなかった）。
そのため切断に気づけず、広告を再開しないまま放置され、
`/info` は「接続中」と嘘をついていた。リンク状態の権威は
`org.bluez.Device1` の `Connected` プロパティに置くのが正しい。

修正後（参加したら接続受け付けを止める + `Device1.Connected` を購読）:

| | 修正前 | 修正後 |
| --- | --- | --- |
| リンク寿命 p50 | 7〜14 秒 | 152 秒（区切りは自分の再起動のみ） |
| 3 分間の再参加 | 22 回 | 0 回 |
| 切断理由 | 器具・電波断・自分が混在 | 自分が切ったぶんだけ |

対策（新アプリ）
- 主リンク 1 本を維持する。 参加したら接続受け付けを止め、
  切れたら再開する（公式アプリの `peripheral_stop_adv_after_welcome` と同じ）
- ⚠️ Android では広告を止められる（BlueZ のように勝手に再開されない）。
  Linux では `ADV_NONCONN_IND` に切り替える必要がある（C33-4）
- 接続状態を UI に 常時明示 する（公式アプリの「接続成功」表示は信用できない）
- 再接続中もユーザー操作を受け付け、キューに溜めて接続後に流す

## I1. ACK・再送が無い片道通信

**内容**
GATT 接続があるので、**スマホと入口の器具の間** はリンク層で再送が保証される。
問題はその先。入口の器具から **メッシュ内の他の器具へ中継される区間には
到達確認が無い**。宛先が受け取ったかどうかは、アプリには判らない。

`DATA_EVENT` を投げても応答は返らない（`MeshCallback.onDataReceived` は
器具側が自発的に流したイベントを拾うだけ）。
つまり アプリ層から見れば依然として片道通信 であり、
「送った」と「届いた」の区別がない。

さらに、GATT 接続そのものが切れていても書き込みが成功したように見えるケースがある
（キューに載った時点で成功扱い）。これが「接続成功しました」表示の直後に
操作が効かない（S5）症状につながりうる。

✅ 実機ログで確定（2026-07-25）

各操作に対して `Handle Value Notification` が 1 回だけ 送られている。

```
+141.1s >> MSGID=0xC1 data=37 37 ...   ← 電源 ON（1 回のみ）
+145.6s >> MSGID=0xC1 data=32 32 ...   ← 電源 OFF（1 回のみ）
+149.4s >> MSGID=0xC1 data=37 37 ...   ← 電源 ON（1 回のみ）
```

到達確認も再送も無い。→ [02-protocol.md](../02-protocol.md) C18-5。

⚠️ 当初の予測「アドバタイズを数百 ms で止めている」は外れ。
実測のアドバタイズ継続時間は 21〜95 秒（中央 36.8 秒） で出しっぱなしだった
（`setTimeout(0)` と整合）。アドバタイズはコマンド送信ではなく参加ビーコンなので、
検証対象は ATT の書き込み回数が正しかった。

対策（新アプリ）
- 器具の状態イベントを監視し、期待した状態になるまで送り直す
  ＝ アプリ層で疑似 ACK を作る。これが安定性の要になる
- ⚠️ 当初「1 コマンドを最低 2〜3 回送る」としていたが、実測で否定された。
  到達率は 1 通で 0.993〜1.000（C33-5）。開ループの連射は上りも下りも
  3 倍にするだけで到達率を上げない。**1 通送って状態応答で確認し、
  届かなかったときだけ再送する** のが正しい
- 確認は実測 RTT の p90 × 2 後に投げる（固定 1500 ms は p90 の 11 倍で無駄に遅かった）
- GATT 書き込みは Write Request（応答あり）を優先し、
  Write Command（応答なし）を使うなら状態応答で確認する

## I2. 状態収集が Ping 応答待ちで、取りこぼす

**内容**
> **訂正**: アドバタイズ受信待ちではなく Ping 応答待ちだった。
> 症状の説明としては同じ構造なので、仮説の骨格は維持される。

`MeshService.API_ping_all()` をブロードキャストで投げ、
各器具が `DATA_CHANNEL_PING_RESPONSE (0xFF)` で応答する。
`MeshCommon.GetPingResponse()` が MAC・vAddr・バージョンを読んで
`DeviceBean` を作り、RTT を記録してリストに積む。

この方式には再送がない。 応答を取りこぼした器具はリストに現れない。
結果として台数が足りず（S3）、状態が空のまま画面が出て（S2）、
応答を待つために起動が遅い（S1・約 7 秒）。

検証方法
- HCI ログで Ping の送信回数と応答数を数える（`timeline` で対応づけ）
- 器具 1 台のみの環境でも 7 秒待つなら固定タイムアウト、
  全台応答で早期終了するなら応答待ち
- 同じ環境で起動を 10 回繰り返し、認識台数がばらつくかを確認

対策（新アプリ）
- 器具リストと状態を永続化 し、起動直後は前回の値を即表示（楽観的表示）
- Ping は起動時の 1 回勝負にせず、バックグラウンドで継続的に投げ続ける。
  応答が来た器具から順に画面を更新する
- 未応答の器具は「不明」として明示しつつ、操作は先に受け付ける。
  公式アプリのように読み込みが終わるまで操作させない設計にしない
- RTT が記録されている（`DeviceBean.setRtt`）ので、
  電波の強い器具を GATT 接続の入口に選ぶ 判断材料に使える

## I3. Android のスキャン回数制限

**内容**
Android 7.0 以降、`BluetoothLeScanner.startScan()` は
**30 秒間に 5 回** を超えると無言で失敗する（例外もコールバックも出ずスキャンが始まらない）。
「数回再検索すると認識する」（S3）という症状は、
再検索のたびに stop/start を繰り返してこの上限に達している疑いがある。

さらに Android 8.1 以降、フィルタなしのスキャンは画面 OFF 時に結果を返さない。

検証方法
`logcat` で `BtGatt.ScanManager` / `AppScanStats` の警告を確認する。
制限に当たると "App … is scanning too frequently" 相当のログが出る。

```powershell
adb logcat -s BtGatt.ScanManager:* AppScanStats:* BluetoothLeScanner:*
```

対策（新アプリ）
- スキャンは stop/start を繰り返さず、開始したら維持する
- `ScanFilter` を必ず指定する（画面 OFF 対策 + 省電力 + 他アプリの結果を拾わない）
- 再検索 UI は「スキャンを再起動する」ではなく「キャッシュを破棄して再収集する」に変える

## I4. アドバタイズ・スキャン・GATT 接続の同時実行 ▼ 確度低下

**内容**
> **▼ 確度低下**: コマンド送信の主経路は GATT なので、
> 「送信のためにアドバタイズを回し続ける」必要はなくなった。
> ただし完全に消えたわけではない。

`MeshCommon.startIBeaconAdvertise` は `setTimeout(0)`（無期限）で呼ばれており、
`createAdvSettings` は `ADVERTISE_MODE_LOW_LATENCY`（約 100 ms 間隔）＋
`TX_POWER_HIGH` を指定している。**止め忘れると最も電力と電波を食う設定で
アドバタイズし続ける**。GATT 接続とスキャンを併走させれば、単一のラジオを 3 者で奪い合う。

検証方法
HCI ログで確認する。

- `LE Set Advertise Enable` の ON/OFF が対になっているか（`summary` が継続時間を出す）
- アドバタイズ有効期間中に ATT の書き込みや Advertising Report が途切れるか（`timeline`）

対策（新アプリ）
- アドバタイズは 必要な瞬間だけ 有効にし、`setTimeout` を明示して自動停止させる
- 常時必要なのはスキャンではなく GATT 接続の維持。優先順位を明確にする
- ラジオを取り合う前提で、「送ったら確認する」を 1 つの単位として扱う

## I5. 機種依存の Peripheral（GATT サーバ）実装差

**内容**
公式が「ペリフェラルモード対応機種」と限定している理由が判明した
（[02-protocol.md](../02-protocol.md) C2）。**スマホが GATT サーバになる** ためで、
アドバタイズのためではなかった。Android の Peripheral 機能は機種差が大きい。

- `BluetoothGattServer` の同時接続数・MTU ネゴシエーションの挙動が機種依存
- `isMultipleAdvertisementSupported()` が false の端末では
  接続可能アドバタイズを出せず、器具から接続してもらえない
- `MeshService.MAX_MTU_SIZE = 214` を要求するが、
  MTU 拡張に応じない端末では既定の 23（`real_mtu = 20`）に留まる
  → セグメント分割が増え、I7 の欠落リスクが上がる
- チップセットによって実際のアドバタイズ間隔や TX パワーが設定値と乖離する

公式アプリは失敗をコールバックで受けてはいる（`onAdvertiseCallback`）が、
`MeshCommon` は独自のエラーコード（101 = アダプタ null、102 = BT 無効、
103 = アドバタイザ取得失敗）を返すだけで、利用者に何が起きたかは伝わらない。

検証方法

```powershell
adb logcat -s MeshCommon:* BtGatt.GattService:* BluetoothGattServer:*
```

`MeshLog` が `TRACE_IO:ADV` プレフィックスで詳細を出しているので、
公式アプリのログをそのまま読める。
`TRACE_IO:ADV:ERROR ... onStartFailure errorCode=` が出ていれば機種依存の失敗。

対策（新アプリ）
- 起動時に端末の BLE 能力を取得してログに残す
  （`isMultipleAdvertisementSupported`、`isLeExtendedAdvertisingSupported`、
  `getLeMaximumAdvertisingDataLength`）
- アドバタイズ・GATT サーバの開始失敗を 必ずユーザーに明示する
- MTU ネゴシエーションの結果を記録し、小さい MTU なら分割数を抑える 方向に倒す
- Central 側で動かせるなら Peripheral を避ける（`join_mode` の選択）

## I6. Android 12+ の権限モデル

**内容**
Android 12（API 31）から Bluetooth の権限が分割された。

| 権限 | 用途 |
| --- | --- |
| `BLUETOOTH_SCAN` | スキャン |
| `BLUETOOTH_ADVERTISE` | アドバタイズ |
| `BLUETOOTH_CONNECT` | 接続・端末情報取得 |

◐ 検証結果：新権限には移行済みだった。ただし位置情報を要求している。

`AndroidManifest.xml` を確認した（`minSdkVersion=23` / `targetSdkVersion=35`）。

```
BLUETOOTH_CONNECT, BLUETOOTH_SCAN, BLUETOOTH_ADVERTISE   ← ✅ 移行済み
ACCESS_FINE_LOCATION, ACCESS_COARSE_LOCATION             ← ★ まだ要求している
BLUETOOTH, BLUETOOTH_ADMIN                                ← 旧 API 用の残置
```

「Android 12+ 未対応」という当初の想定は誤り。 新権限は正しく宣言されている。

ただし `BLUETOOTH_SCAN` に `usesPermissionFlags="neverForLocation"` が付いておらず、
`ACCESS_FINE_LOCATION` を要求し続けている。
そのため利用者は位置情報の許可を求められ、拒否すると動かない。
「権限を全部許可する必要がある」（S8）はこれで説明できるので、I6 は部分的に成立。

`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` / `WAKE_LOCK` / `FOREGROUND_SERVICE` /
`RECEIVE_BOOT_COMPLETED` / `SCHEDULE_EXACT_ALARM` も要求している。
常駐してタイマー機能を動かすためと思われるが、要求する権限の数が多く
利用者の心理的な障壁になっている。

**対策（新アプリ）**
- `BLUETOOTH_SCAN` に `usesPermissionFlags="neverForLocation"` を付け、
  位置情報権限を要求しない（スキャン結果から位置を推定しないため）。
  ユーザーへの説明が減り、拒否による不具合も減る
- 権限が足りない状態を検出して、何が必要か具体的に案内する

## I8. メッシュ中継の輻輳

**内容**
コネクションレス・メッシュは、各ノードが受信パケットを再送して伝搬させる。
重複排除（シーケンス番号）や TTL が不十分だと、
器具が増えるほど同じパケットが飛び交って帯域を埋める（ブロードキャストストーム）。
「器具の真下で操作すると通る」（サカエンの回避策）という現象は、
輻輳ではなく単純な電波到達性の問題を示唆するが、両方が絡む可能性はある。

**検証方法**
器具 1 台のみの環境と複数台の環境で、送信 1 回あたりの成功率を比較する。
台数が増えると悪化するなら輻輳の疑い。

✅ 実測（2026-07-25・器具 2 台）→ [02-protocol.md](../02-protocol.md) C33-5

```
状態要求 142 回 → 応答 141 回/器具   到達率 0.993（両器具）
修正後の再測定                        13/13 = 1.000
```

1 送信 → 1 応答/器具がほぼ厳密に成立していた。 器具 2 台の環境では
輻輳による取りこぼしは観測されていない（3 台以上は未検証）。

⚠️ `odelicd` の `--resend 3` は無意味だった。 上りも下りも 3 倍にしていただけで、
到達率は改善しない。既定を 1 にした。

⚠️ さらに C28-1 の「同じ PDU が二重に届く」を訂正する。
中継による重複ではなく、自分の 3 連射に対する応答 だった。
`resend = 1` にしたら受信重複は 0 件 になった。

対策（新アプリ）
アプリ側からは中継アルゴリズムを変えられない。
できるのは 送信レートを抑えて輻輳に加担しないこと と、
不要なブロードキャストを出さないこと。
→ 1 通送って状態応答で確認し、届かなかったときだけ再送するのが正解
（開ループの連射は帯域を食うだけ・C33-7）。

## I9 / I10. Doze・バックグラウンド制限、電波干渉

**内容**
Doze モードやバックグラウンド実行制限でスキャンが止まる（I9）。
2.4 GHz 帯の Wi-Fi や電子レンジとの干渉（I10）。

いずれも本命ではない。前景で操作する用途が主のため I9 の影響は小さく、
I10 は環境要因で対策の余地が限られる。

**対策（新アプリ）**
- 操作中は前景サービスを使い、スキャンとアドバタイズを維持する
- 干渉は「同じ操作を繰り返しても届かない場合がある」前提の再送設計（I1）で吸収する

## まとめ：改善の核

方式が GATT ベースだと判明しても、結論は変わらなかった。
洗い出した原因は **設計思想の一点** に集約できる。

> 公式アプリは「送ったら届いたことにする」設計で作られている。

これは単なる推測ではなく、`MeshCommon.processSegmentPDU()` が
欠落を検知せず、状態をリセットせず、タイムアウトも持たないという
コード上の事実として確認できた（I7）。
メッシュ内の中継区間には到達確認が無く（I1）、
器具の発見は再送のない Ping 1 回勝負（I2）。
どれも「失敗しないことを前提にした設計」の現れ。

その前提を捨てて、

1. **状態を常時監視し続ける**（読み込み待ちを無くす）
2. 期待する状態になるまで送り続ける（疑似 ACK と再送）
3. すべての操作を冪等にする（途中で失敗しても壊れない）
4. 確認できていないことを「成功」と表示しない
5. 入口の GATT 接続を 1 本に絞って長く維持し、切れたら即座に繋ぎ直す（I11）

1〜4 は当初から変わらず、GATT 方式の判明で 5 が加わった。

⚠️ 5 は当初「冗長化する（複数の器具に同時に繋ぐ）」と書いていたが、実測で覆った。
メッシュはコントローラ 1 台につきリンク 1 本しか許さず、2 本目を迎えると
1 本目が切られる（→ [02-protocol.md](../02-protocol.md) C33-3）。
1 本でも全器具を制御・監視できる ので、冗長化する必要もない。

✅ 1〜5 すべてを `odelicd` で実装し、実測で確認した（2026-07-25・C33）。

| 原則 | 実装と実測 |
| --- | --- |
| 1 | 常時接続を維持。リンク寿命 p50 152 秒（旧 7〜14 秒） |
| 2 | 期待状態まで再送。実測では全件 1 回目で収束（再送不要だった） |
| 3 | プロトコルが絶対値指定なのでそのまま冪等 |
| 4 | 収束を確認できなければ HTTP 504 を返す。`connected` も嘘をつかない |
| 5 | 参加後は接続受け付けを止め、切断を `Device1.Connected` で即検知して再開 |

そして重要なのは、これらが プロトコルの詳細を全部解明しなくても実現できる 点。
Pairlink SDK の Java 層はそのまま使えるので、
上位の再送・状態管理・UI を作り替えるだけで改善できる。
→ 実装方針は [02-protocol.md](../02-protocol.md) の「実装方針への影響」と
[05-app-design.md](05-app-design.md) を参照。
