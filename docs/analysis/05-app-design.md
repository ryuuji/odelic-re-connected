## 方針：完全自前実装（案 D）で確定

⚠️ **この節は当初「暗号化がネイティブ側（`libnative-lib.so`）にあるので
Pairlink SDK の Java 層を流用する（案 C）」としていたが、覆った。**

Raspberry Pi 上で **`.so` も SDK も使わない実装が全機能を達成した**。

| 必要な処理 | 状況 | 根拠 |
| --- | --- | --- |
| GATT サーバ（FFD0 / FFD1 / FFD2）+ ADV_PHONE | ✅ 実証 | [C19](../02-protocol.md) |
| 鍵導出（LOGINKEY / EVENTKEY） | ✅ 完全解明 | [C21-2](../02-protocol.md) |
| 送信の暗号化（AES-128-ECB + PKCS#7 + XOR） | ✅ 実機ログと一致 | [C23-5](../02-protocol.md) |
| 受信の復号 | ✅ 実機ログ全件を復号 | [C23-1〜3](../02-protocol.md) |
| ログイン応答 | ✅ バイト単位で再現 | [C23-2](../02-protocol.md) |
| 照明制御・状態取得・ナイトライト | ✅ 実機で閉ループ確認 | [C23-7 / C24](../02-protocol.md) |
| 他コントローラの操作の追従 | ✅ 実機で確認 | [C28](../02-protocol.md) |

暗号は **標準の AES-128-ECB**（独自 S-box ではなかった）で、
`.so` を呼ぶ必要はない。したがって案 D（完全自前実装）で確定。

✅ 公式アプリのコードもバイナリも使わないため、公開・再配布の余地がある。
（プロトコルの知見は解析による事実の記述であり、コードの複製ではない）

## スコープ（2026-07-25 確定）

### やること

| 機能 | 備考 |
| --- | --- |
| 照明の ON / OFF | `0xC0` / `0xC1` |
| 明るさ・色温度 | 0〜100% ↔ コード変換は [C15-9](../02-protocol.md) |
| ナイトライト（3 段階） | [C24](../02-protocol.md) |
| 一斉 / グループ / 器具個別の指定 | グループは読むだけ（設定はしない） |
| 状態の取得と追従 | `0x70` → `0x71`。他コントローラの操作も観測（[C28](../02-protocol.md)） |
| 器具一覧（MAC / vAddr / 機種 / ファーム / グループ） | 暗号化 Ping の応答から（[C23-4](../02-protocol.md)） |

### やらないこと（スコープ外）

| 機能 | 理由 |
| --- | --- |
| 器具の登録・プロビジョニング（ECDH / `SET_MESH_ENCRY`） | 破壊的。公式アプリに任せる |
| グループ設定の変更（`0x30` / `0x31`） | 同上。読み取りのみ行う |
| HOMEID の発行・変更 | 破壊的（下記）。公式アプリで行い、新アプリは引き継ぐだけ |
| タイマー / スケジュール | 中心機能に絞るため |
| シーン（`0x40`〜`0x42`） | 同上 |
| センサー連携 | 同上 |

⚠️ **これらに対応する送信コマンドは、新アプリに実装しない**（誤送信の余地を残さない）。

## HOMEID の引き継ぎ方式

器具の登録は公式アプリで済ませ、新アプリは「ID を教えてもらって参加する」だけ。
これで破壊的操作を一切実装せずに全機能が動く。

### 手順（利用者から見た流れ）

```
1. 公式アプリの「メニュー」画面を開く → 画面に "ID:12345678" と表示されている
2. 新アプリの初期設定でその 8 桁を入力する
3. 以上。器具の一覧・グループ・状態はすべて自動で読み取られる
```

⭐ 表示箇所は公式アプリのコードで確認済み。
`MenuAct` / `InforUpdateAct` / `MainController` が
`textView.setText("ID:" + Settings.HOMEID + Settings.PASSWORD)` としている。

### 8 桁 ID の分解（公式アプリの `changeID()` と同一）

```java
// LightLoginIDAutoSetAct.changeID()
HOMEID   = meshID.substring(0, 4);      // 上位 4 桁
PASSWORD = meshID.substring(4, 8);      // 下位 4 桁
MeshService.homeid = BleUtil.int2byte(Integer.parseInt(HOMEID));   // 10 進 → LE 4 バイト
MeshService.pwd    = PASSWORD.getBytes();                          // ASCII 4 バイト
```

つまり `12345678` なら

| 項目 | 値 |
| --- | --- |
| HOMEID | `1234` → 10 進 1234 = 0x04D2 → `D2 04 00 00`（リトルエンディアン） |
| パスワード | `5678` → `35 36 37 38`（ASCII） |

→ ここから LOGINKEY / EVENTKEY を導出する（[C21-2](../02-protocol.md)）。

### ⭐ 入力した ID が正しいかを即座に検証できる

器具は接続直後に `PERIPHERAL_LOGIN`（`01 19` + 16 バイト）を送ってくる。
これを LOGINKEY で復号し、**先頭 4 バイトが HOMEID と一致するか** を見るだけで判る
（[C23-1](../02-protocol.md)）。ID の **どちらか半分でも間違っていれば一致しない**。

```
一致した   → ID は正しい。そのまま参加を続ける
一致しない → 「ID が違います」と即座に表示できる（タイムアウトを待つ必要がない）
```

### 引き継がれるもの / 引き継がれないもの

| | 引き継ぎ | 出どころ |
| --- | --- | --- |
| メッシュへの参加 | ✅ | 8 桁 ID だけで足りる |
| 器具の一覧・vAddr・機種・ファーム | ✅ 自動 | 暗号化 Ping の応答 |
| グループ所属 | ✅ 自動 | `0xD0` → `0xD7` 応答 |
| 現在の状態（ON/明るさ/色温度/ナイト） | ✅ 自動 | `0x70` → `0x71` 応答 |
| 器具の表示名・部屋の配置 | ❌ | 公式アプリのローカル DB のみ。新アプリで付け直す |
| シーン・タイマー | ❌ | スコープ外 |

### ⚠️ 注意点

- **下位 4 桁はメッシュのパスワード**。平文で電波に乗る値だが、
  端末内では認証情報として扱う（Android なら `EncryptedSharedPreferences`）
- 公式アプリで **ID を変更すると破壊的**。`changeID()` は
  `deleteData()` → ローカル記録の全削除 + `API_exit_mesh()` を実行する。
  変更したら新アプリ側も入力し直す必要がある
- 公式アプリを一度も設定していない場合の既定値は `11119999`
  （SharedPreferences のキー `HOMEID` / `PASSWORD` の default が `1111` / `9999`）
- 新アプリと公式アプリは 同時に使える（[C28-3](../02-protocol.md) で実証）

## 設計の原則

公式アプリの問題は「送ったら届いたことにする」設計に起因する。
その逆を徹底する。

| # | 原則 | 効果 |
| --- | --- | --- |
| P1 | 状態は常時監視してキャッシュする | 起動時の読み込み待ちを無くす（S1 S2 S3 の解消） |
| P2 | 期待する状態になるまで送り続ける | 片道通信の取りこぼしを吸収（S3 S4 S7 の解消） |
| P3 | すべての操作を冪等にする | 途中で失敗しても器具の状態が壊れない（S5 S6 の解消） |
| P4 | 確認できていないことを成功と表示しない | 「接続成功」の嘘をやめる（S5 の解消） |
| P5 | 操作を待たせない | 楽観的 UI で即応答。確認は裏で走らせる |

P1〜P4 が安定性、P5 が体感速度を担う。

## 技術選定

| 領域 | 選定 | 理由 |
| --- | --- | --- |
| 言語 | Kotlin | Android の標準。Coroutines / Flow が BLE の非同期処理に適合する |
| UI | Jetpack Compose | 状態駆動の UI が P5（楽観的更新）と相性が良い |
| 非同期 | Coroutines + Flow | 受信 PDU のストリーム、送信の直列化とスロットリングを素直に書ける |
| 状態保存 | DataStore（Preferences） | 器具リスト・最終状態の永続化。軽量で十分 |
| DI | 手書き or Hilt | 規模次第。当初は手書きで足りる |
| minSdk | 26（Android 8.0） | 拡張アドバタイズと安定した BLE API が使える。5.0 対応は捨てる |
| targetSdk | 最新 | 権限モデルに正面から対応する（I6 の解消） |

minSdk を 26 にする判断について
公式アプリが Android 5.0 対応を維持していることが、
古い BLE API の使い方を引きずる原因になっている疑いがある（I3 I6）。
自分用のアプリなので互換性を切り捨てて、新しい API を正しく使う方を取る。

## CommandScheduler の設計（中核）

安定性のほぼ全部がここに乗る。

### 責務

1. **キューイング**: 未接続のあいだ操作を溜め、リンク確立の瞬間に流す
2. **再送**: 観測状態が期待状態に一致するまでコマンドを送り続ける（P2）
3. 収束判定: 一致したら送信を止め、UI に確定を通知する（P4）
4. 諦め: 一定時間・一定回数で収束しなければ失敗として報告する

⚠️ 当初想定していた「送信と受信の時分割」は不要だった。
器具の状態はアドバタイズではなく GATT リンク上の応答 で返ってくる（C23）ので、
スキャンとアドバタイズがラジオを奪い合う問題（I4）は起きない。

### 送受信サイクル ✅ 実測値で確定（2026-07-25 → [02 C33](../02-protocol.md)）

```
コマンドを 1 通送る（Notify）
   ↓ T_confirm（実測 RTT の p90 × 2 = 約 200〜275 ms）
状態要求 0x70（ブロードキャスト 1 通で全器具が応答・C23-8）
   ↓
0x71 応答をデコードして収束判定
   ├─ 一致 → 確定（UI を確定表示に）
   └─ 不一致・無応答 → 再送し、T_confirm を 1.6 倍に伸ばして繰り返す
4 回試すか 3 秒を超えたら「届かなかった」と表示する（P4）
```

| パラメータ | 値 | 根拠（実測） |
| --- | --- | --- |
| 1 操作の送信回数 | 1 通 | 到達率 0.993〜1.000。連射は上りも下りも 3 倍にするだけで到達率を上げない（C33-5） |
| `T_confirm`（初回） | RTT p90 × 2（下限 200 / 上限 800 ms） | 実測 p90 は 60〜137 ms。固定 1500 ms は p90 の 11 倍で無駄に遅かった |
| `T_confirm`（再送時） | 前回 × 1.6 | |
| 最大試行 / 期限 | 4 回 / 3 秒 | 実測では全件 1 回目で収束した（再送不要） |
| 収束までの実測 | 277〜320 ms（p50 312 ms） | 「操作 → 器具が実際にその状態になったと確認」までの時間 |
| 即応答（楽観的 UI） | 5.3〜5.9 ms | 収束は裏で追う（P5） |
| スライダーの連続操作 | 120〜143 ms でコアレス | 公式アプリと同じレートで送っても、最新値以外は破棄して収束は最終値だけ追う |

⭐ 状態要求 → 応答の RTT 実測（1 通・接続パラメータ最適化後）:
`p50 50〜78 ms / p90 60〜92 ms / max 77〜117 ms`。

⚠️ in-flight の状態要求は 1 本に制限する。
`0x70` にはシーケンス番号のフィールドが無いので、応答をどの要求に
対応づけるかは「直近の 1 本」で決めるしかない
（RTT の p99 が 450 ms 未満なので、要求間隔を 200 ms 以上に保てば衝突しない）。

⚠️ **接続パラメータを確認すること。** notify のレイテンシは Connection Interval に
律速される。器具は 15.00 / 28.75 ms を指定してくるが、**Linux では BlueZ が
勝手に 45 ms へ書き換えていた**（C33-2）。Android では
`BluetoothGatt.requestConnectionPriority()` が Central 用なので Peripheral では使えない。
器具の指定を尊重するのが最善。

### 期待状態と観測状態

- ユーザー操作で「期待状態」を更新 → UI は即座にそれを表示（P5）
- 器具が返す `0x71` 応答（および他コントローラのコマンド観測）が「観測状態」
- 両者が一致 → 確定。UI の暫定表示を確定表示に変える
- 一定時間一致しない → UI に「届いていない」ことを明示する

期待状態を上書きする新しい操作が来たら、古い操作の再送は破棄する。
明るさを連続で動かした時に古い値が送られ続けると操作感が壊れる。

### 冪等性（P3）✅ プロトコル側が既に絶対値だった

**good news。** 照明制御コマンドはすべて絶対値指定だと確認できた
（[02-protocol.md](../02-protocol.md) C15-4）。

```
{own(4), 0xC0, sub=0, 明るさコード, 色温度コード, 0,0,0,0}
```

「1 段上げる」のような相対操作は存在しない。ON/OFF も特殊コード（55 / 50）の絶対指定。
→ 同じコマンドを何度送っても結果は同じ。再送しても二重に効かない。

つまり P3 は **プロトコルを変えずに達成できる**。
必要なのは「再送する仕組み」だけで、「冪等になるよう変換する層」は要らない。

⚠️ グループ設定・シーン登録は スコープ外（送信しない）。
ただし 受信側の分割 PDU の再組立は実装する（長い応答が分割されて届くため・C30）。

### 収束判定の具体（P2・P4）

状態応答のフォーマットが判ったので、期待状態と観測状態を **直接バイト比較できる**。

```
送信: {0xC0, sub=0, bright, cct}
   ↓
状態要求: {0x70}                       ← パラメータなし
   ↓
応答:   data[4]=0x71, data[5]=cct, data[6]=bright
   ↓
判定:   data[5] == cct && data[6] == bright  → 収束
```

ON/OFF も同じ経路で確認できる（`55/55` = ON、`50/50` = OFF が
コマンドと応答の **両方で同じコード**）。

⭐ 注意: 明るさコードは逆順（0 が最も明るい、19 が最も暗い）。
色温度は順方向。UI のスライダー値との変換で符号を間違えやすい。

コマンドと状態応答で式が完全に同一 なので、変換は 1 か所にまとめられる
（[02-protocol.md](../02-protocol.md) C15-9 / C18-4 で実機確認済み）。

```kotlin
/** 色温度・明るさ（0〜100%）とプロトコルのコード値を相互変換する。 */
object LightCode {
    fun colorToCode(percent: Int): Int = (percent / 5).coerceIn(0, 20)
    fun codeToColor(code: Int): Int = code * 5

    /** 明るさは逆順。0% は特別値 19。 */
    fun brightToCode(percent: Int): Int =
        if (percent == 0) 19 else ((100 - percent) / 5).coerceIn(0, 19)
    fun codeToBright(code: Int): Int = 100 - code * 5

    const val CODE_ON = 55    // 0x37 — 値域外の状態コード
    const val CODE_OFF = 50   // 0x32
}
```

⚠️ ON / OFF の `55` / `50` は 0〜20 の値域外。
**明るさ・色温度の連続値と同じバイト位置に入るので、
「今は状態コードか値か」を型で区別する** 設計にしないと事故る。
`sealed interface LightTarget { data class Level(...); object On; object Off }` のように分ける。

## BleTransport の設計

### 端末能力の検査

起動時に取得してログに残す（I5 の切り分け用）。

- `BluetoothAdapter.isMultipleAdvertisementSupported()`
- `isLeExtendedAdvertisingSupported()`（API 26+）
- `getLeMaximumAdvertisingDataLength()`（API 26+）
- アドバタイズ開始の成否

### アドバタイズ（公式アプリの実測値と一致させる・C31-3）

- `ADVERTISE_MODE_LOW_LATENCY`（実測 100〜131 ms 間隔）
- `ADVERTISE_TX_POWER_HIGH`
- ⭐ `setConnectable(true)`。器具がこちらに接続してくるのでこれは必須
- `setTimeout(0)`（無期限）
- AD の中身: `C0 FF | 05 | HOMEID(4) | 識別子(6)` を company ID 0 の
  Manufacturer Specific Data に入れる（31 バイト以内）
- 識別子の 6 バイトは **永続化した疑似 MAC**（端末の MAC ではない・C31-1）
- `onStartFailure` を **必ず UI に伝える**。黙って失敗しない（I5）
- ⭐ 切断を検知したら必ずアドバタイズを再開する（C32）。
  広告アドレスは Android 任せでよい（器具は見ていない）

### スキャン → 不要

⚠️ 当初は「器具のアドバタイズをスキャンして状態を得る」設計を想定していたが、
**器具は普段アドバタイズしない**（C19-4）。状態は GATT リンク上で取る。
→ **スキャンは実装しない。** `BLUETOOTH_SCAN` 権限も要らない。

### 権限

- 必要なのは **`BLUETOOTH_ADVERTISE`** と `BLUETOOTH_CONNECT` だけ
  （スキャンしないので `BLUETOOTH_SCAN` も不要 → **位置情報権限は一切要求しない**・I6 の解消）
- 常駐のため: フォアグラウンドサービス + `foregroundServiceType="connectedDevice"`（Android 14+）、
  電池最適化の除外、`WAKE_LOCK`、起動時自動開始
  （公式アプリも同じ構成を取っている）
- 不足時は「何のために何が必要か」を具体的に案内する

## UI 方針

- **起動即操作可能**。読み込み画面を作らない（P1 P5）
  - 前回の状態を即表示 → 受信したら差分更新
- 明るさ・色温度は **スライダーで連続操作** し、操作中は送信をスロットリング、
  指を離したら最終値の収束を待つ
- 器具・グループごとに「確定 / 送信中 / 未到達」の 3 状態を 視覚的に区別 する（P4）
- 初期設定は 8 桁 ID の入力だけ。誤りは `PERIPHERAL_LOGIN` の復号で即座に検出できる
- 器具の表示名はアプリ内で付ける（公式アプリからは引き継げない）
- 破壊的操作（グループ変更・器具登録・ID 変更）は実装しない。
  必要になったら公式アプリで行う旨を案内する

## 実装の着手順

プロトコル未確定でも進められるものから。

プロトコルが解明できたので、**上から順に素直に進められる**。

1. **プロジェクト骨組み**（Kotlin / Compose / minSdk 26）
2. プロトコル層の移植 — `odelicd/odelicd.py` を Kotlin に移す。
   公式アプリのコードは使わない（案 D）。暗号は標準の AES-128-ECB で足りる
   ```kotlin
   // 公式アプリのメニュー画面に出ている 8 桁 ID をそのまま入力してもらう
   val displayId = "12345678"
   val homeid = ByteBuffer.allocate(4).order(ByteOrder.LITTLE_ENDIAN)
       .putInt(displayId.substring(0, 4).toInt()).array()          // D2 04 00 00
   val pwd = displayId.substring(4, 8).toByteArray(Charsets.US_ASCII)  // 35 36 37 38
   val inter = byteArrayOf(homeid[0], pwd[0], homeid[1], pwd[1],
                           homeid[2], pwd[2], homeid[3], pwd[3])
   val loginKey = inter + "LOGINKEY".toByteArray()   // 受信ログインの復号・応答用
   val eventKey = inter + "EVENTKEY".toByteArray()   // データの暗号化・復号用
   ```

   ⚠️ HOMEID は数値のリトルエンディアン、パスワードは ASCII。変換方法が違う。
3. `MeshSession` — 参加シーケンスと PDU の解釈。受信を `Flow` で公開
4. 参加と器具発見 — GATT サーバ + アドバタイズ → 器具が接続 →
   `PERIPHERAL_LOGIN` に応答 → `GET_PASSWORD` に応答 → WELCOME →
   暗号化 Ping で器具一覧（MAC / vAddr / 機種 / ファーム）を取得
   → この時点で「器具が見えて個別に指定できる」ところまで到達する
5. 状態監視 — `{0x70}` で状態要求、`0x71` 応答をデコード（C15-9）
   → ここまでで P1（読み込み待ちゼロ）が成立する
6. `CommandScheduler` — 期待状態に収束するまで再送。フェイク Gateway で単体テスト
7. 照明制御 — `0xC0` サブコマンド 0（明るさ・色温度）と ON/OFF（55/50）
   → 最小限の実用アプリがここで完成
8. UI（Compose）
9. ナイトライト（`0xC0` サブコマンド 1 / `0xC5`）と他コントローラの追従（C28）

⚠️ グループ設定・シーン・タイマー・器具登録は スコープ外（実装しない）。

手順 4〜5 が最初のマイルストーン。 器具が見えて状態が読めれば、
公式アプリの最大の弱点（起動 7 秒・状態が反映されない・台数が足りない）を
その時点で解消できていることになる。

ブロッカーは残っていない。 手順 1 から順に着手できる状態だった（→ ⛔ 中止）。

## ⭐ Pi での実証から来る必須事項（C31〜C33）

⚠️⚠️ ここがこの文書でいちばん価値のある部分。
Raspberry Pi で実際に動かして測って初めて判ったことで、
ネイティブアプリを書くなら言語やプラットフォームに関係なく必要になる。

### 接続の維持（ここを外すと「不安定なアプリ」が再生産される）

- ⭐⭐⭐ 参加したら接続の受け付けを止める（C33-3）。これが安定性の核心。
  広告を出し続けると器具が次々に繋いできて、**そのたびにメッシュが古いリンクを切る**
  （新リンク確立の 0.7〜1.4 秒後・完全な交互）。メッシュは
  「コントローラ 1 台につきリンク 1 本」しか許さない
  - ⚠️ Linux では広告を消せない（BlueZ が 150〜240 ms 後に再開する）ので
    `ADV_NONCONN_IND` に切り替える。**Android では素直に止められる**
- ⭐ リンクは 1 本で足りる。冗長化しない（C33-3）。
  メッシュが中継するので、繋いでいない器具の状態も RTT 78 ms で返ってくる
- ⭐ 切断の検知は接続状態の変化で行う（Android なら `onConnectionStateChange`、
  BlueZ なら `Device1.Connected`）。BlueZ の `StopNotify` は当てにならない
  （24 h で確立 50 回に対し切断 2 回しか通知されなかった・C33-8）
- 切断時は残っている接続を確実に片付けてから 広告を張り直す（C32）。
  ⚠️ 古い ACL リンクが残っていると同じアドレスでは再接続してこない
  （→ これを「アドレスを覚えられている」と誤解していた。[history.md](history.md) の 3）
- ⭐ `PERIPHERAL_LOGIN` に正しい応答を返す（C23-2）。
  これをしないと器具が数秒で切断し、状態も返さない
- ⭐ `SET_LINK` (`01 10`) を主リンクに送らない（C23-6）。
  送ると器具が「バックアップ扱い」にして応答を返さなくなる
- アドバタイズの設定 は LOW_LATENCY（実測 100〜131 ms）/ TX HIGH / 接続可 /
  タイムアウトなし。AD には 永続化した疑似 MAC（アプリ層の identity）を入れる
  （公式アプリは `SharedPreferences` に保存している・`BleUtil.getBTMac`）

### レイテンシと確認

- ⭐ **Connection Interval を確認する**（C33-1 / C33-2）。器具は 15.00 / 28.75 ms を
  指定してくる。notify のレイテンシはこれに律速される
  - ⚠️ Linux では BlueZ が 45 ms に書き換えるので `conn_min_interval` を下げる
- ⭐ **1 操作 = 1 通で足りる**（C33-5）。到達率は 0.993〜1.000。
  3 連射は上りも下りも 3 倍にするだけだった。
  ⚠️ 「同じ PDU が二重に届く」現象も 自分の連射が原因 だった
- ⭐ 確認は実測 RTT の p90 × 2 後に投げる（C33-7）。固定 1500 ms は p90 の 11 倍
- 明るさスライダーは中間値を連射しない（公式アプリは 143 ms 間隔で 16 通送っていた）
- コマンドはすべて絶対値指定 なので、同じものを再送しても二重には効かない（冪等）

### 送受信の実装

- 送信は宛先ごとに送り分け、送信完了を待って直列化する
  （Android は `notifyCharacteristicChanged(device, …)` +`onNotificationSent`。
  公式アプリと同じ。⚠️ BlueZ にはこれができない）
- **操作はキューに溜め、接続の瞬間に流す**（未接続時に「成功」と言わないため）
- **MTU は 217 が期待値**（`real_mtu = MTU - 3 = 214`）。切断時は 20 に戻す（C29-5）
- 参加したら暗号化 Ping → 器具一覧（vAddr）を確保してから個別制御・状態要求
- 受信 `type 0x06` を復号して状態に反映（鍵はログイン要求から。リンク単位）
- ⭐ 他コントローラのコマンド（平文 `0xC0`/`0xC1`/`0xC5`）を観測して状態に反映（C28）。
  重複排除と、確認のための状態要求（デバウンス）まで込みで
- ⭐ 分割 PDU（タイプ `04 04`）の再組立を自前で正しく実装（C30）。
  ⚠️ 公式アプリの実装は 1 個落ちると 以降の分割転送が二度と完成しない

### 常駐

- フォアグラウンドサービス + `foregroundServiceType="connectedDevice"`（Android 14+）
- 電池最適化の除外、`WAKE_LOCK`、起動時の自動開始（公式アプリもこの構成）

⭐ すべて `odelicd`（[../../odelicd/odelicd.py](../../odelicd/odelicd.py)）に実装済みで、
**実機で 24 時間以上動いている**。移植元として読める。
