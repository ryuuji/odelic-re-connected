## 1. 製品概要

**[事実]** ODELIC「CONNECTED LIGHTING for HOME」は、調光調色 LED 照明器具・調光対応 LED 照明器具を
リモコン／スマートフォン／タブレットから無線制御するシステム。

**[事実]** インターネットを一切使用しない。したがってクラウド API は存在せず、
制御は端末と器具の間の BLE ローカル通信のみ で完結する。外出先からの操作は不可。
→ 解析対象は BLE 通信に限定でき、サーバ側の解析は不要。

[事実] 停電復帰時は直前の点灯状態を保持する。器具側に状態の不揮発保存がある。

[事実] 調色範囲は 電球色 2700K 〜 昼光色 6500K（製品スペックで確認・2026-07-26）。
⭐ プロトコル上の `color` は 0〜100% の抽象値（5% 刻み・21 段。→ [C15-9](../02-protocol.md)）で
ケルビン値を持たないので、この対応づけが必要だった。
実機で `color = 0%` を送ると電球色になる ことも目視で確認済み。
→ Matter の mired 換算に使っている（→ [07 M4](../07-matter.md)）。

[事実] 初回接続設定（器具登録）時には壁スイッチの操作が必須。
→ 器具側は電源 ON 直後の一定時間だけ「登録受付モード」に入る設計と考えられる [推測]。

[事実] メーカーサポートは操作不能時の説明として「メッシュネットワークが不安定」と回答している。
→ ODELIC 自身がメッシュ構成であることを認めている。

出典: [製品ページ](https://www.odelic.co.jp/products/connectedlighting/) /
[よくあるご質問](https://www.odelic.co.jp/products/connectedlighting/qa/) /
[サカエン Developer's Blog](https://www.saka-en.com/iphone/odelic-iphone-android-application/)

### コントローラごとの上限

| コントローラ | グループ／PLACE 数 |
| --- | --- |
| リモコン RC-911A / RC-912A | 6 グループ |
| 単リモコン RC-917A / RC-918A / RC-919A | 1 グループ |
| タブレット版「for Home」 | 12 PLACE |
| スマートフォン版 | 6 グループまでを推奨 |

**[事実]** 照明器具 1 台に対しリモコンは 4 台まで登録可能。
**[事実]** リモコンとスマートフォンなど、異なるコントローラの併用が可能。

→ 器具側に「登録済みコントローラ」のテーブルがあり、上限がある [推測]。
→ スマホが「4 台まで」の枠を消費するのかは不明 [要検証]。消費するなら、
  開発中に何度も再登録すると枠を食い潰す危険があるため、解析前に確認したい。

[事実] 「ネットワークの構築のため、正常に動作するまでに数分かかる場合があります」との公式記述。
→ 器具間でメッシュの経路構築フェーズがある、もしくは単に登録処理が遅い [推測]。

#### ⭐ 最重要の手がかり：「Bluetooth ペリフェラルモード対応」

**[事実]** 公式が動作条件として「Bluetooth ペリフェラルモード対応の機種」を挙げている。

これはプロトコル方式を決定づける情報。ペリフェラルモード（BLE Peripheral role）が必要ということは、
**スマートフォン側がアドバタイズ（電波を発信）する側** だという意味。
一般的な BLE 家電アプリはスマホが Central（スキャンして接続する側）なので、この要件は出てこない。

→ 詳細な考察は [02-protocol.md](../02-protocol.md) を参照。

[事実] アプリサイズが 9.8 MB と小さい。
→ 巨大な SDK やゲームエンジンは含まれない。難読化されていなければ逆コンパイルで十分読める規模 [推測]。

### ⭐ OTA ファームウェアが同梱されている

**[事実]** `assets/ota/` に 22 ファイル。拡張子は `.mp3` だが音声ファイルではない
（MP3 のマジックバイトを持たず、全ファイルが共通のバイナリヘッダで始まる）。
器具のファームウェアイメージと考えられる。サイズは約 29〜33 KB。

```
10_2_0.mp3  11_2_0.mp3  12_2_0.mp3  13_2_0.mp3  14_2_0.mp3
18_2_0.mp3  19_2_0.mp3  20_2_0.mp3  21_2_0.mp3  37_2_0.mp3
38_2_0.mp3  4_2_0.mp3   5_2_0.mp3   6_2_0.mp3   7_2_0.mp3
8_2_0.mp3   9_2_0.mp3
20292_4_5.mp3  20307_4_11.mp3  20308_3_5.mp3
```

**[推測]** 命名は `<製品コード>_<major>_<minor>`。
数値が `MeshService.PRODUCT_CODE_*` と一致する（例: `14` = 0x14 = `DOWNLIGHT_60`、
`21` = 0x15 = `DOWNLIGHT_100`）。5 桁のものは別系統の型番。

→ 器具側のファームウェアが解析できる。Java から読めない `.so` の暗号処理や
器具側のコマンド解釈を、ファームウェアの逆アセンブルから追える可能性がある [要検証]。

⚠️ OTA 機能そのものには絶対に触らない。 器具を文鎮化させる危険がある。
ファイルを読む解析だけに留める。

## 3. 報告されている不具合（症状カタログ）

解析で「何を再現し、何を直すのか」の基準になるので、症状を具体的に記録する。

| # | 症状 | 出典 |
| --- | --- | --- |
| S1 | アプリ起動後、約 7 秒の読み込みが入る（戻るボタンで中断しても操作は可能） | ユーザーレビュー |
| S2 | 起動時、現在の点灯状態が操作画面に反映されないことが多い | サカエン |
| S3 | 器具 3 台中 2 台しか認識せず、数回の再検索で全台認識 | サカエン |
| S4 | グループ設定の保存失敗率が非常に高い | サカエン |
| S5 | 「接続成功しました」と表示された直後に、調光・調色操作が一切効かなくなる | サカエン |
| S6 | S5 の復旧には「ID 変更」から器具登録を初期化して再ペアリングが必要 | サカエン |
| S7 | タイマー設定時に明るさが意図した値にならない | ユーザーレビュー |
| S8 | Bluetooth を常時 ON にし、権限を全許可しないと動かない | ユーザーレビュー |

### 症状から読み取れること [推測]

- **S1 + S2 + S3** は同じ根に見える。「器具の現在状態を集めるのに時間がかかり、集めきれないことがある」。
  状態を能動的に読み取る手段（GATT Read / Notify）がなく、
  器具側が定期的に流すアドバタイズを受動的に拾って集めているなら、この挙動は自然に説明できる。
  取りこぼせば台数が足りず（S3）、間に合わなければ状態が空のまま画面が出る（S2）。
- **S4 + S5 + S6** も一貫している。設定書き込みが到達確認のない片道通信で、
  複数パケットに分割されているとすれば、途中の欠落で器具側の設定が半端な状態に壊れる。
  壊れた状態はアプリからは直せず、初期化しか手がない（S6）。
  「接続成功しました」の表示が実際の到達を意味していない（S5）のも、片道通信なら整合する。
- S8 は Android 12 以降の `BLUETOOTH_ADVERTISE` / `BLUETOOTH_SCAN` 権限、
  および位置情報権限の要求が古い実装のまま残っている可能性。

→ いずれも「コネクションレス（アドバタイジングベース）通信で、ACK と再送が無い」という
  一つの仮説で説明できる。この仮説の検証が解析の主目的になる。

## 4. 無線モジュール

**[事実]** 調査の出発点にした参考情報から、Pairlink 社（`pairlink.com.cn`）の
BLE 技術が関係する。→ <https://www.pairlink.com.cn/pl-web/product/ble-spec>

**[事実]** 伊藤電機（`ito-elec.jp/ble/`）が Pairlink 製 BLE モジュールを取り扱っており、
現在同ページに掲載されているのは以下 3 品番。

| 品番 | 仕様 |
| --- | --- |
| PLTBEITO | Bluetooth 5.0、メッシュネットワーク対応（SIG mesh／独自メッシュ） |
| PLRBNEITO | Bluetooth 5.0、パターンアンテナ搭載 |
| PLDBEITO | Bluetooth 5.0 + Classic(EDR) デュアルモード |

[事実] 調査の初期に控えた `PLTCEOC-05` は、現在の同ページには掲載がない
（旧品番か別ページの可能性）。→ 後に 器具が GATT で公開している型番 だと判明
（[02 C18-6](../02-protocol.md)）。

[事実] Pairlink 公式サイト（`pairlink.com.cn/pl-web/product/ble-spec`）は
JavaScript による動的読み込みのため、通常の取得では本文が読めなかった。
→ ブラウザでの手動確認、または JS 実行を伴う取得が必要 [要検証]。

### ✅ 確認済み：Pairlink「Connected Mesh」SDK を使用

**[事実]** 静的解析で確定した。公式アプリには
`com.pairlink.connectedmesh.lib` パッケージが難読化されずに丸ごと含まれている。
SIG mesh ではなく Pairlink の独自メッシュ。

当初の推測（独自メッシュだろう、`com.pairlink.*` を探せば判る）は当たったが、
「ペリフェラルモード必須だからコネクションレス方式だろう」という推測は **外れた**。
実際は GATT ベースで、スマホが GATT サーバ（Peripheral role）になるモードがあるためだった。
→ [02-protocol.md](../02-protocol.md) の C1・C2 を参照。

[事実] `libnative-lib.so` に `pairlink` 文字列が 18 箇所、`AES` が 11 箇所。
暗号化はネイティブ側で行われ、鍵は HOMEID + パスワードから導出される。

## 5. 識別子 ✅ 解明済み

**[事実]** アプリが表示する 8 桁の「ID」は
**上位 4 桁が HOMEID、下位 4 桁がパスワード** の連結。

```java
commitSp("HOMEID",        id.substring(0, 4));
commitSp(Define.PASSWORD, id.substring(4, 8));
```

変換方法が両者で違う（HOMEID は数値、パスワードは文字コード）。
当初の推測「下位はネットワーク内の個体／グループ番号」「BCD 表記かもしれない」は
どちらも 外れ。→ 詳細は [02-protocol.md](../02-protocol.md) の C16。

### 現在の値（これが唯一の正）

| 項目 | 値 | バイト列 |
| --- | --- | --- |
| アプリの ID 表示 | `12345678` | — |
| HOMEID | `1234` | `D2 04 00 00`（10 進 1234 = 0x04D2 の LE） |
| パスワード | `5678` | `35 36 37 38`（ASCII） |

出所: 利用者の実機で確認（2026-07-25）。

**[事実]** この分割規則は 2 つの異なる 8 桁 ID で裏付けた。
解析の途中で ID を変更・再ペアリングしたため、変更前の値でも同じ規則が
成り立つことを確認できた。

⚠️ **旧値そのものはリポジトリに書かない。** 下位 4 桁はメッシュのパスワードで、
無効化済みであっても公開する意味がない。規則の裏付けという役割は
「2 例で確認した」という記述だけで果たせる。

[要検証] HOMEID とパスワードが `.so` 内でどう鍵に変換されるか（AES の鍵導出）。
